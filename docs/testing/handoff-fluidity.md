# Hand-off fluidity: goals, tests and how to measure a real desk

The goal: moving to the other PC feels like moving to an extra monitor. No
wait at the border, no change in where the cursor is or how fast it goes, and
coming back straight away works. Either PC's own mouse and keyboard can take
over at any time, and nothing is ever left pressed.

## Goals

| Metric | Goal |
|---|---|
| Crossing: crossing → first motion on the other screen | ≤ 16 ms (one frame) in the simulator; p90 ≤ 16 ms on a real desk |
| Entry point (proportional mapping) | within 1.5 px of the crossing point |
| Coming back right after crossing | works 50 ms after the crossing, with no ping-pong |
| Resting at the border | no flapping, no cursor flash |
| Buttons and keys | never left pressed, on any PC, also over a lossy network |
| Cursor hide/show on GNOME | ≤ 3 ms (extension v9, measured in headless GNOME) |

## Where each goal is tested

| What | Test | Runs |
|---|---|---|
| Every OS pair × side × screen size × scenario (2052 cases) | `src/desk_sim/fluidity_matrix.rs` (generated by `scripts/gen-fluidity-matrix.py`, scenarios in `fluidity.rs`) | the user's layout (171) on every `cargo test`; all weekly |
| Two people using both PCs at once, random and seeded | `src/desk_sim/random_walk.rs` | 5 walks on every `cargo test`; long walks weekly |
| Bad networks (loss, jitter/reordering, duplicates) | `src/desk_sim/bad_network.rs` | 4 on every `cargo test`; the rest weekly |
| Network edge cases on real DTLS | `src/net_tests/` | every `cargo test` |
| Cursor hide/show delays on a real GNOME Shell | `the_cursor_reappears_with_the_first_movement_after_a_return` in `input-emulation/tests/gnome_headless.rs` | `scripts/gnome-headless.sh --test`, weekly CI |
| X11 return hand-off | `a_push_out_through_the_entry_edge_is_the_return` (`input-emulation/src/x11.rs`) | every `cargo test` |
| Windows: physical mouse takes over | `only_physical_moves_and_presses_take_the_mouse_back` (`input-capture/src/windows/event_thread.rs`) | Windows CI runners |

The weekly job is `desk-matrix` in `.github/workflows/test-quality.yml`
(`cargo test --lib -- --ignored desk_sim::`).

### OS models in the simulator

`src/desk_sim/screen.rs`, `Personality`:

| OS | Capture | Return detection | Buttons known | Own mouse noticed while driven |
|---|---|---|---|---|
| gnome | libei portal; activation backswing, border jitter | emulation (absolute tracker) | yes, via the cursor extension | no (one shared cursor) |
| windows | low-level hooks; injected crossings seen by capture | emulation | yes, via the hook | yes (`LLMHF_INJECTED`) |
| sway | layer-shell strip on the edge pixel, touched by the injected pointer too | capture strip (wlroots cannot report the pointer) | no; the Wayland implicit grab keeps a drag on its window | no |
| x11 | none (receive only) | emulation (`XQueryPointer`) | n/a | n/a |

No KDE model: it would only be a copy of the baseline with another name, and
there is no measurement to calibrate one.

## What the matrix found and fixed

- **A quick return to a sway PC was lost.** A return within 300 ms of
  entering (`REMOTE_ENTRY_DWELL`) was ignored, and on wlroots nothing else
  reports it. Now a return during that window counts when the peer's last
  injected motion pushed out through the entry edge. Jitter is never an
  outward push.
- **An X11 PC could not be left with the mouse.** The X11 emulation never
  reported the push past the entry edge. It does now, using `XQueryPointer`.
- **Grabbing the driven PC's mouse did nothing.** On Windows the last hand
  that moves now wins (`CaptureEvent::LocalActivity`).
- **A drag crossed the border.** The button was left held in the app on the
  source PC. The new `drag_across` option is `hold` by default: the edge's
  barrier is taken away while the button is down, and the cursor rests at the
  edge. `cross` lets go of the button on the source PC first. On wlroots a
  drag always holds, because of the Wayland implicit grab.
- **Local injection dropped a button release** that had no press through the
  same handle (`InputEmulation::consume_untracked`).
- **Both PCs could drive each other (a loop).** This was found by the random
  walks. Pointer motion from a peer that had not entered (it overtook its
  `Enter`, or trailed its `Leave`) was injected as if it were local. It pushed
  this PC's own pointer over its barrier and started a capture back. Now motion
  only applies from a peer that entered (`src/emulation.rs`, test
  `motion_from_a_peer_that_has_not_entered_is_not_applied`).
- **A button let go in the very moment a drag was held at the edge stayed
  down** in the app. The release went to the capture being given back. Now it
  is given back to this PC.

Two limits of the test setup, not of the app:

- every service watches its config file, and Linux allows 128 inotify
  instances per user by default, so the walks run two desks at a time;
- heavy loss *combined with* heavy duplication (10 % + 5 %) keeps the DTLS
  handshake of `webrtc-dtls` from ever completing. Each alone is fine, and real
  links do not duplicate at such rates, so the profiles test them separately.

## Measuring a real desk

1. Turn the trace on, on both PCs:
   `LAN_MOUSE_HANDOFF_TRACE=1` (Linux: `systemctl --user set-environment
   LAN_MOUSE_HANDOFF_TRACE=1` and restart the service).
2. Use the desk normally for a while. Cross both ways, come back quickly,
   type and click on the other PC.
3. Summarize:

   ```sh
   scripts/analyze-handoff-trace.py --report --since 2026-11-25
   ```

   This prints the crossing latency, the gaps between inputs while moving,
   stalls (25–100 ms gaps) per 1000 inputs, and how often return motion was
   dropped.

Baseline on the user's desk (Ubuntu 26.04 Wi-Fi 6E ↔ Windows 11 Wi-Fi,
2026-11-24/25, before this work):

| | Value |
|---|---|
| Windows → Ubuntu, enter → first input | p50 5.4 ms, p90 13.3 ms |
| Gaps while moving | p50 7.9 ms (125 Hz mouse), p99 43 ms |
| Stalls per 1000 inputs | 24.8 |
| Ubuntu → Windows, begin → first motion sent | p50 0.2 ms, p90 0.3 ms |
| Probe loss | 0.0 % (RTT p99 108 ms: Wi-Fi delay spikes, not loss) |

The stalls are Wi-Fi delay spikes, outside the app (see
`docs/latency-plan.md`). With 0 % loss, motion redundancy would not help, so it
was not added.

## Not done yet

- **Windows pointer acceleration** ("Enhance pointer precision") when Windows
  drives another PC: available, opt-in (`windows_pointer_acceleration = true`).
  The Windows capture then forwards what Windows itself makes of each mouse
  report. The cursor is held at the centre of its display, every move is
  blocked in the low-level hook, and its target minus the held point is the
  motion. Measured on the Windows CI runners: 117 counts became 197 px with
  the curve on, and the peer got the same within 10 % (`raw counts × speed`
  sends ~60 % of it). Off by default until it is checked with real mice:
  absolute devices (tablets, remote desktop) fall back to the raw path.
- **The driven PC's own mouse on GNOME, sway and X11.** The physical mouse and
  the peer's virtual pointer move one shared cursor and cannot be told apart,
  so the driver keeps control until its own mouse comes back. Nothing gets
  stuck and there is no loop.
