## 2. Residual risks / needs real hardware or a live desktop session

- X11 INCR read/write and XFixes detection are compile-verified only. Manual: paste >256 KiB both ways between an X11 app and a peer; copy twice in the same app and confirm the second copy syncs; confirm a stuck owner read times out (10 s) and does not wedge the backend.
- Wayland/portal restart recovery (SVC-01): requires a real GNOME/KDE session where the portal session is killed (lock/unlock or compositor restart). The retry path reuses the portal restore token, so it should not re-prompt; validate no prompt loop.
- Windows F15 listener retry and clipboard-lock scope: compile-verified with the x86_64-pc-windows-gnu target only; needs a Windows run (ideally with a Clipboard manager/Office holding the clipboard) to validate contention and retry behaviour.
- macOS TIFF fallback is dormant code: only cargo check --target x86_64-apple-darwin was run; needs a real macOS run (Preview/Screenshot -> paste on peer).
- Config atomic save vs concurrent writers (daemon + a frontend/CLI writing config): single-writer in the current architecture (frontends go through IPC), but if a second writer is ever added the last-write-wins lost-update race remains. Residual risk documented; an mtime/generation check was not added because no second writer exists.
- Audit log growth: bounded to 5 MB + one 5 MB rotation. The source-side peer_permissions dedupe (XC-02) is still needed to stop filling those 10 MB with redundant rows; the audit-side helper only helps once the service calls it.
- Clipboard transfer is DTLS/UDP with retransmission and a 1.2 s abort window; on very high RTT links a transfer can abort (surfaced as status.last_error / Cancel), not silent.
- config.toml unknown keys and comments are still dropped on save (the existing TODO in src/config.rs): writing merges nothing, it replaces the file from the in-memory ConfigToml. Not fixed here because a DocumentMut merge is a risky refactor for a release-blocking QA; the atomic write + corrupt-file backup guarantee no data loss, only comment/unknown-key loss. Document this in the release notes if users hand-edit the file.
- The X11 backend now uses XFixes when the server advertises it; on the rare X server without XFixes it falls back to owner-id polling, which still cannot see a second copy from the same owner (pre-existing limitation, now only for that fallback).
