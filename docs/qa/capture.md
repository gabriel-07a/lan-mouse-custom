# QA ledger — input-capture audit (task-1, capture-auditor)

Scope: input-capture/ only (lib.rs backend selection + bookkeeping, layer_shell.rs,
libei.rs, x11.rs stub, windows.rs, windows/event_thread.rs, windows/display_util.rs,
macos.rs dormant, dummy.rs, error.rs, build.rs). Cross-checked prior audits:
docs/audit-cross-os.md (F4/F6/F7/F8/F12), docs/audit-windows-permissions.md (§3.2 H1,
§5 P0), docs/audit-cursor-return.md (C1), docs/audit-ubuntu-permissions.md,
docs/qa-repro-matrix.md. No production input devices or GUI were exercised; only pure
functions, mock backends and cargo checks cross-targets.

Baseline: cargo build/test workspace green before the audit. Final state:
cargo test -p input-capture = 29/29 pass; clippy -p input-capture --all-targets = clean;
cargo check -p input-capture for linux, x86_64-pc-windows-msvc, x86_64-apple-darwin and
all feature combinations (none, layer_shell, libei, x11, all) = clean.

## Prior-audit backlog verification (Lead)
- docs/audit-windows-permissions.md §3.2 H1b / §5 P0 (a): PostThreadMessageW(...).unwrap() in Drop was ALREADY replaced by a retry+log before this audit (partially stale); the remaining race was the thread id published before the message queue existed, and a failed post could still hang Drop's join. Both are fixed now (C3).
- §3.2 H1 (b) GetMessageW panic: was still present at HEAD -> fixed (C3).
- §3.2 H1 (c) thread_id before message queue: was still present -> fixed with PeekMessageW + handshake (C3).
- docs/audit-cross-os.md F6 (mixed DPI / enumeration): capture now uses EnumDisplayMonitors like the emulation backend and refreshes entry point + scale on WM_DISPLAYCHANGE/WM_DPICHANGED (C10/C11). Residual: needs hardware validation in a 100%+150% layout.
- docs/audit-cross-os.md F7 (absolute raw input): fixed with delta conversion (C9); residual: digitizers whose absolute units are neither 0..=65535 nor virtual-pixel are still ignored (previous behavior), needs tablet hardware.
- docs/audit-cross-os.md F8 (macOS bounds only grow): fixed (C16), dormant code compile-checked only.
- docs/audit-cross-os.md F12 (libei session restart on device change): intentional per GNOME workaround (LM_RESTART_SESSION_ON_DEVICE_CHANGE documented in code); each restart closes the session and drops its EIS stream in the cleanup path, no fd/state leak found beyond the pre-existing GNOME v1 prompt limitation. No change.
- docs/audit-cursor-return.md §3.2 (Windows per-edge suppression / 120 ms injection grace / REMOTE_ACTIVE replacement): verified, no stuck-suppression found; suppression is per edge (edge_activation_allowed), cleared on RemotePeer(None), and the release cooldown is cleared when a peer takes over. The new injected-event guards only apply while a remote peer drives the machine and cannot latch (time-based).
- docs/audit-cross-os.md F4 (X11 capture): CONFIRMED still a stub at HEAD (x11.rs returns X11InputCaptureCreationError::NotImplemented; auto-selection logs it and continues). README/features advertise x11_capture however. Needs a product/docs decision (crossos owns README/DOC.md); not fixed here because implementing X11 capture is a feature, not a QA hardening fix.
- docs/audit-cross-os.md F3 (key repeat for Linux receivers): still open and out of input-capture scope by itself (capture would need to synthesize repeat from wl_keyboard.repeat_info; emulation-side dedupe owns the bug). Reported, not changed.
- docs/audit-windows-permissions.md §3.1 "Probes Windows sao infaliveis por construcao": now stale after C3 - the capture probe can legitimately fail when the capture thread cannot set up (previously it silently claimed the backend while capture was dead). WindowsInputCapture::new is fallible now; doctor --probe reports the real state.

## Residual risks / manual validation
1. Wayland compositor crash/restart (C1): unit-testable only with a compositor; manual check: kill the compositor while lan-mouse runs -> daemon must log "layer-shell input capture connection lost" and not spin (top shows low CPU); capture must be reenabled (GUI Reenable) after the compositor is back.
2. Sway/Hyprland display hotplug and capture teardown while grabbed (C4): no pointer lock/shortcut-inhibitor leftovers; cursor restored.
3. Windows mixed-DPI + hotplug (C10/C11): barriers on the outer edge only, pointer speed logical-consistent across 100/125/150/200%, WM_DISPLAYCHANGE handled while capturing.
4. Windows absolute devices (C9): tablet/stylus and RDP sessions must move the remote pointer and cross barriers; direction must match the device.
5. Windows injected events (: when another peer drives this machine, no key/mouse feedback loop; concurrent capture+receive is an unsupported configuration but must not loop.
6. macOS (dormant): bounds recompute after hot-unplug, tap death surfaces as capture error and restores the cursor, multi-display hidden cursor still unverified (audit-cross-OS H3).
7. libei portal: user denies the permission dialog or never answers it -> daemon shutdown must not hang (C14); activation without barrier id/cursor position only logs and keeps the session alive.
8. VirtualKey/XTest paths untouched (input-emulation owned by another agent).

## Post-release round (v0.2.7 user report) - R-02 fixed: one portal session per run

| ID | Sev | Location | Symptom | Root cause | Fix |
|---|---|---|---|---|---|
| R-02 | P1 (UX) | input-capture/src/libei.rs do_capture/do_capture_session | On Ubuntu/GNOME the "allow input capture" dialog appeared on every hand-off/activation ("o tempo todo") | the capture loop cancelled and closed the portal session on every client-set change, zones change and EIS device change, then created a new session for the next activation. GNOME's InputCapture portal is v1: it cannot persist consent, so every CreateSession shows the dialog again | ONE portal session is created per app run and reused: capture/release cycles keep the session (and the EIS connection) alive; client changes and ZonesChanged only re-establish pointer barriers; activations without an enabled client are released immediately; the session is only recreated if the portal/EIS fails (bounded 3 attempts, falling back to the previous behaviour). The LM_RESTART_SESSION_ON_DEVICE_CHANGE workaround is gone. |

Note: InputCapture v1 (GNOME 50 as shipped by Ubuntu) has no restore token, so at most ONE prompt per
lan-mouse launch can be guaranteed; with portal v2 (KDE and newer compositors) the token makes the
consent persist across restarts as well. The dialog is only requested when the first client starts
capturing (never on a receive-only machine).
